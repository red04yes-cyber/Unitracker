# Study Planner Engine

## Scope

This slice implements the planner domain/service layer and persists accepted
study blocks through the existing SQLite-backed CalendarEvents collection.
It does not add a second calendar, a second database, demo records or XAML.

## Contracts

- StudyPlannerOptions defines the planning date range, IANA/Windows timezone
  ID, recurring weekly availability, weekly and daily study budgets, preferred
  and minimum block lengths, breaks, daily block count and whether the user
  explicitly requested replacement of prior generated planner blocks.
- StudyAvailabilityWindow is a local wall-clock window for one weekday.
  Windows cannot cross midnight; represent overnight availability as two
  windows on adjacent weekdays.
- StudyPlannerService.CreatePreview(data, options, generatedAt) is read-only.
  It returns StudyPlanPreview.Blocks, UnscheduledTasks and warnings. It never
  edits tasks or calendar events.
- StudyPlannerService.Apply(data, preview, appliedAt) rechecks current tasks
  and calendar conflicts, then creates indicative CalendarEvent entries.
- StudyPlannerService.ApplyAndSaveAsync(...) persists through the existing
  IStudyDataStore SQLite transaction. If saving fails, the in-memory
  CalendarEvents collection is restored.
- ClearGeneratedPlan(...) deletes only unchanged blocks generated by this
  planner inside the requested date range. The UI should make this an explicit,
  confirmed action.

## Scheduling rules

1. Only open tasks (Todo or InProgress) with a positive EstimatedMinutes
   are schedulable. Completed and cancelled tasks are never rescheduled.
2. Tasks are considered by earliest due date first, then priority (5 to 1),
   creation timestamp and stable ID. An overdue task may still receive
   catch-up blocks, but the preview warns that the original deadline has passed.
3. Every proposed block must fit inside one of the user's explicit availability
   windows, the selected date range, the task deadline (when still in the
   future), the remaining weekly/daily budgets and the per-day block count.
4. Blocks are split at PreferredBlockMinutes. BreakMinutes are left as
   unbooked gaps between consecutive blocks; breaks are not credited as study.
5. All non-cancelled calendar events are treated as occupied time, including
   lectures, exams, deadlines, personal commitments and previously generated
   study blocks. The planner never moves an existing event.
6. Weekly and daily budget usage deducts unique ledger minutes already
   recorded, plus future calendar commitments categorized Study or Review.
   Overlapping intervals are unioned to avoid double counting.
7. No availability means no proposed times. The planner does not infer a user's
   free time from an empty calendar.
8. Preview output is indicative. Applying it creates events with
   Source=Planner, Verification=Indicative and Category=Study. Planning a
   task does not start a timer or change the task status.
9. IDs are stable (ExternalId prefix study-plan:v1:); applying the same
   preview twice is idempotent. Apply rechecks for calendar conflicts to avoid
   overwriting a meeting added after preview generation.
10. A replace-generated-plan request removes only unchanged events created
    by this service. A generated event whose UpdatedAt is later than
    CreatedAt is treated as user-edited and is preserved as a commitment.

## Timezone and DST

Availability is authored in the requested timezone. Invalid local times during
the spring-forward gap are shifted forward to the first valid minute and a
warning is returned. For an ambiguous autumn time, the start boundary uses the
earlier instant and the end boundary uses the later instant, preserving the
full available interval. Calendar event timestamps remain absolute
DateTimeOffset values.

## Persistence and migrations

No migration is required: planned blocks reuse the already-persisted
CalendarEvents table and the existing CalendarEvent source, verification,
timezone and external-ID columns. ApplyAndSaveAsync uses IStudyDataStore.
Planning options and weekly availability are provided explicitly to the
preview call; the presentation/settings layer must load the user's saved
preference values into StudyPlannerOptions before preview generation.

## UI binding contract

- Render preview blocks separately from saved calendar events until the user
  confirms application.
- Show unscheduled task titles, remaining minutes and the reason returned by
  StudyPlanUnscheduledTask.
- Show weekly/daily budget usage, scheduled minutes, block count and warnings.
- Mark planner events as indicative; do not label them as official lectures or
  confirmed exams.
- Support changing/moving/deleting a block through the existing calendar CRUD
  service. A user-edited generated block is preserved if a plan is regenerated.
- Regenerate plan must be a confirmed action; pass
  ReplaceExistingGeneratedBlocks=true.
- After ApplyAndSaveAsync, refresh the calendar from the persisted StudyData
  snapshot. Do not mark source tasks completed or create activity-ledger entries
  merely because blocks have been planned.
- To start work from a planned block, call the existing focus/Pomodoro flow
  explicitly and link the resulting session to the task/course.

## Task-linked focus progress

- Selecting an open task in the existing Study Lab task list and starting the
  focus timer links the generated timer activity to that task. If the task has
  a course, that course takes precedence over the separate focus-course picker;
  if the topic field is empty, the task title is used as the focus topic.
- ActivityLedgerService.SyncFocusSession accepts an optional task ID and stores
  it in the existing StudyActivities.TaskId column. Repeated synchronization
  preserves the link and updates the same activity row; no new table or schema
  migration is required.
- PomodoroService.Start accepts the same optional task ID. Subsequent pause,
  resume, break and completion transitions keep the link through the existing
  idempotent ledger synchronization.
- ActivityLedgerService.GetTaskProgress derives recorded seconds from actual
  focus segments and completed manual ledger intervals. It unions overlapping
  timer/manual intervals, excludes pause gaps and soft-deleted activities,
  clamps the progress bar at 100%, and reports estimate overruns separately.
  An estimate of zero is shown as unconfigured rather than as 100% complete.
- A cancelled timer still contributes focus segments actually recorded before
  cancellation. A cancelled non-timer activity remains excluded.
- Removing a task that is referenced by activity history changes an open task
  to Cancelled instead of deleting its row. This preserves the TaskId foreign
  reference and audit trail; unreferenced tasks are still physically removed.
- The existing WPF workspace exposes SelectedTaskProgress,
  SelectedTaskProgressDisplay, SelectedTaskProgressPercent,
  SelectedTaskRemainingMinutesDisplay and SelectedTaskOverEstimate for binding.
  The current XAML remains owned by the UI workstream; no visual layout change is
  included in this service-layer slice.

## Progress-aware planning

- StudyPlannerService.CreatePreview obtains task progress through
  ActivityLedgerService.GetTaskProgressSnapshots, which scans recorded intervals
  once for all open tasks. Planned minutes are based on each task's remaining
  estimate, not its original estimate.
- Remaining seconds are rounded up to whole minutes so a partial minute is not
  silently omitted from the proposed workload.
- Timer/manual overlaps are unioned by the ledger; soft-deleted and cancelled
  manual activities do not reduce the estimate. Recorded focus segments from a
  cancelled timer remain credited according to the ledger rules.
- StudyPlanPreview.TaskProgress exposes the point-in-time snapshots used to
  build the proposal. RecordedTaskMinutes and RemainingTaskMinutes provide
  aggregate values for a preview summary; these are derived values, not stored
  counters.
- If an open task has already consumed its estimate, the preview does not
  schedule another copy of the estimated work. It returns a zero-minute
  unscheduled entry and a warning so the student can update the estimate or
  complete the task.
- Apply compares the preview snapshots with current task progress. If recorded
  work or the estimate changed after preview generation, the affected blocks
  are rejected and a replacement remains all-or-nothing. It also rejects a
  proposal whose aggregate minutes exceed the current remaining estimate.
- Legacy previews use HasTaskProgressSnapshot=false and retain the previous
  estimate-based validation path for compatibility. New previews always set
  the flag and provide a non-null progress collection; it must contain a
  snapshot for every task referenced by a block. Partial or duplicate snapshot
  sets are rejected rather than falling back.
- Invalid persisted weekly/daily budgets are clamped to the supported limits
  for preview generation and explained in warnings. Availability is limited to
  64 windows per week and an applied preview to 3,620 blocks (181 days × 20
  blocks/day) to bound malformed input processing.

## Validation

Tests in StudyPlannerServiceTests cover:

- splitting around fixed calendar commitments;
- no fabricated availability and unscheduled reasons;
- deduction of unique recorded ledger time from daily/weekly budgets;
- deadline and priority ordering;
- idempotent apply and preservation of task status;
- stale-preview conflict detection;
- safe replacement of unchanged generated blocks;
- preservation of user-edited generated events;
- SQLite persistence round-trip;
- ambiguous autumn and invalid spring DST boundaries;
- task-link idempotence, course inference and cross-course rejection;
- unique task-time progress across overlapping timer/manual intervals and pause gaps;
- actual focus time retained when a timer is cancelled;
- task-history retention on removal, zero-estimate behavior and estimate overruns;
- task-linked Pomodoro startup and rejection before partial session creation;
- SQLite round-trip of the existing StudyActivities.TaskId field;
- scheduling only the unrecorded remainder of a task;
- rounding partial remaining minutes upward;
- overlap union, task isolation, soft deletion and cancelled manual entries;
- estimate exhaustion warnings for tasks that remain open;
- stale-preview rejection after additional work is recorded;
- rejection of blocks exceeding the remaining estimate;
- malformed/excessive availability and oversized preview rejection;
- clamping invalid persisted study budgets;
- compatibility with previews created before task-progress snapshots.

The progress-aware planning slice adds fifteen focused planner tests. GitHub
Actions must pass before this slice is considered verified; no local
build/test result is claimed in this document.
