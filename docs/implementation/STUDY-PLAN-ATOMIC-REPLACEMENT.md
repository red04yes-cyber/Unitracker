# Safe study-plan preview application

## Problem

Applying a replacement preview previously removed the existing unchanged planner
blocks before validating the new preview against the current tasks and calendar.
If a task had been completed or a new appointment had appeared after preview
generation, the replacement could be only partially applied (or entirely
rejected) after the previous plan had already been deleted.

An empty replacement preview could also clear the previous plan without an
explicit clear action.

## Behavior

- Validate that preview dates and timezone match the validated planner options.
- Revalidate task existence and open status at apply time.
- Reject blocks when the task title, course, deadline or effective priority has
  changed since preview generation.
- Reject a preview when its aggregate planned minutes exceed the task's current
  estimate.
- Validate block duration, planning-window boundaries and that a block has not started more than two minutes before apply (a short
  grace period avoids rejecting a preview while the user confirms it).
- Re-resolve the course name from the current local snapshot rather than copying
  potentially stale display text from the preview.
- Recheck existing calendar conflicts and duplicate external IDs at apply time.
- Stage new events before mutating the shared calendar snapshot.
- In replacement mode, preserve the previous generated plan if the preview is
  empty or any proposed block is stale, invalid, or in conflict. Replacement is
  all-or-nothing; valid staged blocks are not partially committed.
- Remove only unchanged events generated by this planner. User-edited generated
  events and manual/imported/official calendar events remain untouched.
- Keep explicit clearing available through `ClearGeneratedPlan`; an empty
  replacement preview is not treated as a clear command.
- Reject `DateOnly.MaxValue` as the end of an explicit clear range before
  calculating the exclusive next-day boundary.

## Verification

`StudyPlannerServiceTests` adds 14 regression cases covering:

1. Existing-plan preservation after a new calendar conflict.
2. Existing-plan preservation when a task is completed after preview.
3. Existing-plan preservation for an empty replacement preview.
4. All-or-nothing replacement when one of multiple blocks conflicts.
5. Preview metadata/options mismatch.
6. Blocks outside the requested date range.
7. Block duration inconsistent with planned minutes.
8. Task title changes after preview.
9. Reduced task estimates after preview.
10. Task deadline changes after preview.
11. Blocks that started beyond the two-minute apply grace period.
12. Current course-name resolution at apply time.
13. Safe rejection of a clear range ending at `DateOnly.MaxValue`.
14. Null entries in a malformed preview collection.

The existing tests continue to cover idempotent application, calendar conflict
rechecks, preservation of user-edited planner blocks, SQLite persistence,
daylight-saving transitions and explicit removal.

## Scope and limitations

- No schema or migration changes.
- No new dependencies or network services.
- No XAML, visual resources or navigation changes.
- No AI, model provider or AI Study Director changes.
- The planner still uses the task's estimated minutes as its source workload.
  It does not yet subtract task-linked completed focus time; that requires the
  separate task-progress integration to be present in the target branch.
- The implementation does not automatically move official, imported or
  user-created calendar events.

The Windows CI workflow should run the complete .NET 10 test suite, WPF Release
build, self-contained win-x64 publish, startup smoke test and packaging. The
security workflow independently runs Gitleaks and blocking NuGet audits.
